# Event Calendar Strategy

The brief proposes the national event calendar as the highest-priority build and asks whether it should become the center of the platform. Honest answer: no. The calendar is valuable, but it is a Phase 2 feature, and it must not be the center. The center is the recurring table. A calendar is a supporting layer that only has value once there is real local activity to put on it.

## Why the calendar should not be the center

- An empty calendar is worse than no calendar. A national calendar with three events in most cities signals a dead community and damages trust. Calendars need density first.
- A calendar is a directory, and directories are low-defensibility. A funded competitor can scrape and replicate a list of public events quickly. Our moat is local trust and recurring habit, not a list.
- The thing that makes a player return weekly is their own game and a local nudge, not browsing a national calendar. Calendars are reference tools, checked occasionally, not habits.
- Building national calendar software now pulls engineering away from the one job that matters: proving recurring tables. It is the classic "build the impressive thing" trap.

## What the calendar is actually good for (later)

Once a city is dense, a local calendar becomes genuinely useful: it is the answer to "what mahjong is happening near me this week," and it feeds the weekly newsletter. At that point it reinforces the loop. So the calendar is a Phase 2 local feature, not a Phase 1 national build.

## Manual first, software later

We do not need calendar software to have a calendar. For the next 90 days:
- The "calendar" is a section in the weekly local newsletter: this week's open plays, new tables, and any local event. Curated by hand from what the ambassadors and the founder know.
- Event submission is an email to hello@ or a simple form; the founder or ambassador places it in the newsletter. No build.
- This proves whether anyone cares about a calendar before we build one, and it generates the content that would fill a calendar anyway.

Only build calendar software when the manual version is clearly straining (too many events to hand-curate across several dense cities). That is a good problem and a long way off.

## If and when we build it

Design, for Phase 2 or 3:
- City calendars first, national as an aggregation of city calendars. Local is where the value and the trust are.
- Event types: open plays and new recurring tables (the core, high-frequency, habit-forming items) front and center; tournaments, leagues, retreats, cruises, and fundraisers as occasional listings.
- Submission with light review (we vet for safety and realness, consistent with the trust moat). Never list an event we cannot verify.
- Tie every event to the core actions: an open play listing has a "save my seat" path; a new table has "claim a seat." The calendar should create tables and seats, not just inform.

## Challenge summary

The calendar is a Phase 2 supporting feature, run manually inside the newsletter until a city is dense enough to need software. It is not the center of the platform and it is not the highest-priority build. The highest-priority build is no build at all for 90 days; it is forming recurring tables. Putting a calendar at the center would be optimizing the lobby of a building that has no rooms yet.
